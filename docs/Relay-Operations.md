# Relay operations

## Configuration

| Setting | Required | Purpose |
| --- | --- | --- |
| DISCORD_PUBLIC_KEY | Yes | Hex public key from the real Discord application's Developer Portal. |
| StorageQueueAccount | Yes | Storage connection string with Queue and Blob access. |
| DISCORD_QUEUE_NAME | No | Queue name; default discord-interactions. |
| DISCORD_DEDUP_CONTAINER | No | Private blob container; default discord-interaction-receipts. |
| ENABLE_ED25519_SIGNING | No | Missing, invalid, or false disables signing and key generation. |
| DISCORD_TEST_PRIVATE_KEY | Only when signing is enabled | Separate raw Ed25519 test private key encoded as hex. |

The old DISCORD_PRIVATE_KEY setting is no longer read. Never copy a configured private key into logs, source control, or responses. Remove obsolete secrets after confirming migration. If the old anonymous signer was publicly reachable with a configured key, rotate that key and replace its public key wherever it was trusted. A Discord Developer Portal public key is not generated by this app.

Startup checks configuration syntax without contacting storage. A valid signed Discord ping can therefore succeed during a storage outage. Invalid or missing required configuration prevents startup with a setting-specific error.

## Signing helper and Discord verification

Discord signs its own verification ping; the public /api/discordrelay endpoint verifies it and responds with {"type":1} without queue access. Saving the Interactions Endpoint URL in Discord does not require enabling the signing helper.

For manual test signing:
1. Configure DISCORD_TEST_PRIVATE_KEY with a test-only key pair.
2. Set ENABLE_ED25519_SIGNING=true temporarily. Azure application-setting changes restart the app.
3. POST the exact test body to /api/Ed25519SignFunction with a valid Function key in the x-functions-key header.
4. Use the returned timestamp and signature as X-Signature-Timestamp and X-Signature-Ed25519; send the identical original body.
5. Test against a separate test app configured with the corresponding test public key, never by replacing the real Discord app's public key.
6. Set ENABLE_ED25519_SIGNING=false afterward and confirm the helper returns 404 when called with a valid Function key. Without a key, the Functions host may reject the request before the flag is evaluated.

GenerateEd25519KeyPair also requires the flag and a Function key. It returns a newly generated test private key intentionally; the signing endpoint never returns the configured private key. Bootstrap a test key locally or from an existing test key store before enabling the helper.

## Storage and duplicate processing

Provision the queue and private receipt container before deployment. scripts/Prepare-RelayDeployment.ps1 validates the Azure runtime, provisions those resources using the existing app connection setting, and forces signing off. The deployment identity needs permission to read app settings and update the signing flag. The connection needs queue and blob creation/access permissions. No queue/container creation occurs during requests.

Incoming signatures must be at most 300 seconds old and no more than 30 seconds in the future. Keep app clocks synchronized. Types 2, 3, and 5 require a Discord interaction ID; unsupported types and invalid bodies are rejected before storage access.

Each interaction ID has a receipt blob. A 15-second lease serializes concurrent handlers across instances. Only a confirmed queue send is marked complete. Completed retries return the same deferred response without sending another message. A held lease or unavailable storage returns 503. Lease release is bounded; failed release recovers by expiration.

The request has a two-second processing budget, including body reading and storage calls, plus up to 150 milliseconds for lease cleanup. Azure SDK retries are disabled on that path. Cold starts, network delays outside application code, or platform scheduling may still exceed Discord's three-second deadline; monitor latency and choose appropriate hosting capacity.

Queue and receipt updates are not a single transaction. If a send succeeds but its response or completion update is lost, a retry can enqueue another copy. Delivery remains at least once. Downstream consumers MUST use Result.id as a persistent idempotency key and atomically couple their completion record with their business side effects, or use the destination API's idempotency feature. Marking done before the side effect can lose work; marking afterward without an atomic transaction can repeat it. The downstream consumer is outside this repository and must be updated/verified before claiming end-to-end idempotency.

Receipt blobs contain no payload or interaction token. They are retained by default. An operator may configure a storage lifecycle retention of at least seven days, comfortably exceeding the five-minute signature window. Do not remove active receipts during testing or deployment.

## Build and test

Use .NET SDK 10. Start Azurite 3.35.0 with default local Blob and Queue ports (10000 and 10001). Tests create isolated randomly named resources and remove only those resources. To use another dedicated test storage account, set RELAY_TEST_STORAGE to its connection string.

From the repository root:
```powershell
dotnet restore Src/CSharp/Azure/SovereignTrust.Relay.Azure/SovereignTrust.Relay.Azure.csproj
dotnet test Tests/SovereignTrust.Relay.Tests/SovereignTrust.Relay.Tests.csproj --configuration Release
dotnet publish Src/CSharp/Azure/SovereignTrust.Relay.Azure/SovereignTrust.Relay.Azure.csproj --configuration Release --output artifacts/relay
```

To run only unit tests without Azurite, add --filter "Category!=Storage". Actual Function-key enforcement is performed by the Functions host; unit tests verify the trigger authorization declaration, and a deployed smoke test must verify rejection without the key.

## Development and production release

- Pushes to main_publish build, test with Azurite, upload the complete publish directory (including .azurefunctions), then deploy development.
- Pull requests only build and test.
- Manual development runs are allowed only on main_publish.
- The production workflow is manual only. Run it on main_publish after validating development and supply the development workflow run ID.
- Production verifies that the selected run was a successful development deployment on main_publish and deploys that exact run's artifact. It does not rebuild or promote a pull-request artifact.
- Both deployments verify .NET 10 isolated hosting, provision storage, and set ENABLE_ED25519_SIGNING=false. Linux Consumption is rejected; Flex Consumption, Premium, and Dedicated support .NET 10.
- The production action is an explicit promotion trigger, not an enforced GitHub reviewer gate. Add environment reviewer protection if organizational policy requires separate approval.

Development acceptance checks:
1. Confirm unsigned/invalid-signature relay requests return 401.
2. Save the real Discord interaction URL and confirm ping verification succeeds.
3. Send a real command, confirm prompt acknowledgment, and inspect the queue for Result.id.
4. Retry a signed test interaction on the separate test app and verify a single normal enqueue.
5. Confirm signing is disabled and requests with a valid Function key return 404.
6. Verify consumer duplicate behavior before promoting production.

After deployment, remove/rotate any previously exposed key as appropriate. Do not treat a build or emulator test as evidence that real Discord verification, Azure access policies, or downstream effects have been validated.
